## 3. 迭代划分

### R1 —— 质量与安全加固（P1，先行）
F-42 → F-43 → F-44 → F-45。理由：F-45 E2E 体系建成后再开 R2/R3 的功能迭代，回归保护全程在位；F-44 注入防护是外部内容（web_fetch/MCP）进入上下文的兜底，越早越好。

### R2 —— 会话体验补全（P2）
F-46 → F-47 → F-48 → F-49。全部围绕「会话」这一核心对象：分叉重跑、终端、MCP 生态补全、导出分享。

### R3 —— 分发与规模（P2/P3）
F-50 → F-51 → F-52 → F-53。面向「给别人用」：自动更新、Windows 安装、市场、性能。

## 4. 关键依赖与风险

| 风险 | 影响 | 缓解 |
|------|------|------|
| node-pty 原生模块（F-47） | 跨平台编译与 SEA/Electron 打包复杂度 | 复用 desktop 既有 npmRebuild 链路；CLI 形态可延迟到 R3 |
| 自动更新签名（F-50） | macOS 公证 / Windows 签名需要证书 | 先做「检查 + 提示 + 跳转下载」的手动通道，热更新后置 |
| MCP streamable HTTP（F-48） | 协议新、参考实现少 | 仅接官方 spec 已稳定部分，experimental 能力不接 |
| E2E 依赖真实 LLM（F-45） | CI 不稳定 | E2E 全部走 Fake Provider（既有测试基建），不依赖真实网络 |
| 市场（F-52）供应链 | 安装第三方 Skill 脚本的安全面 | 安装时强制展示 scripts/ 清单并确认，接 F-44 注入防护与权限模式 |

## 5. 交付口径

- 每个特性独立分支 `feat/F-xx-slug`，docs 与代码分开提交（沿用现行仓库规范）。
- 门禁不变：`pnpm typecheck` / `pnpm test` / `pnpm smoke`（涉 Web 加 `pnpm smoke:web`）；R1 完成后 E2E（F-45）纳入门禁。
- 每特性交付后在本文档勾选状态并回写 `docs/PRD.md` 需求池。
